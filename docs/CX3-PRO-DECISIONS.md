## D10 功能实现优先、完整测试集中收尾 — ACCEPTED（2026-10-25）

用户明确选择：先实现所有适用功能；中间简单验证；完整测试独立规划并最后执行。生效文档：[v4功能计划](CX3-PRO-FEATURE-FIRST-PLAN.md)、[最终测试计划](CX3-PRO-FINAL-TEST-PLAN.md)。本决策覆盖旧阶段全量验收阻止后续编码的顺序，不降低最终功能范围，不把stub/离线编译称硬件PASS，也不自动授权部署/设备初始化。日常不重复全套host/mutation/审计，相关失败或最终集成时才扩大回归。

D04的当前实现路线选用受控用户态服务，默认不开机安装；D04的运行/恢复验收仍开放。其余决策只在相关功能需要时收敛，不把全清单预先评审设为每项编码门槛。

## D00 开放接口策略 — ACCEPTED

用户确认：系统原生网络优先；RDMA、时间戳等平台缺通用入口的能力可通过配套用户态 SDK/工具开放。
不由此推导必须复制 Linux 内核 ABI、不推导必须 DriverKit 重写，也不允许用软件 TCP 模拟冒充硬件能力。

## D01 本卡能力与拓扑 — OPEN；阻塞：高级功能范围、速率目标

问题：当前 PN/PSID/FW、逐端口 supported/current type 与 speed、PCIe 宽度、模块/线缆以及每项原始 cap 是什么？

- 已知：VPD MCX354A-FCCT；官方手册将该型号列为 VPI；历史 FW 2.42.5000；Linux旧日志Gen3 x4；PSID未知。
- 不能继续使用“PCI class是ETH所以不是VPI”的旧结论；手册列的常见PSID也不能冒充本卡PSID。
- 决策产物：本卡能力/固件组合表、raw+解码、实物/拓扑、家族候选与板级可用能力差异、可支持的端口配置、遗漏cap补账。
- 关闭条件：每项结论可追溯；未知项有准确原因和下次取得证据的动作；不必为了盘点刷写固件。

## D02 故障安全与历史冻屏 — OPEN；阻塞：P1-S/日用发布

问题：资源撤销、锁次序、命令超时、客户端关闭、DMA与中断的哪一条不变量可能导致卡死？如何证明修复或安全隔离？

- 输入：`HANG-AUDIT.md`、`DEFECTS.md`、远端探针历史、各启动的版本身份和最后阶段。
- 先形成故障树与证据表：panic、watchdog、内核无响应、单链路中断、USB键盘失效不能混为一类。
- 闭环：已知触发场景 → 最小变量实验或离线回归 → 故障前后观察 → 可证的资源安全条件。
- 关闭条件：所有可复现阻塞缺陷修复并回归；无法归因的历史事件保留“未归因”说明及风险，不把一轮未复现称根治。安全门与长期门均需通过。

## D03 RSS QPC 读回与内部多队列 — OPEN；阻塞：P1-R/F15/F16

问题一：RSS入口 QUERY_QP 的通用字段失配，是特殊布局/字段覆盖、解码错误，还是状态损坏？

- 已保存线索：CQN sent128/read0x004d4e4f，低三字节与key[13:16]一致；其它字段也有变化；仅有解码结构不足以证明规范语义。
- 先采集完整发送context与raw QUERY_QP；普通RX QP作对照。独立启动只改RSS key，QPN/CQN/环几何保持不变，检查异常值是否跟随key、资源/流量是否一致；不在当前活跃会话强行重建。
- 关闭条件：取得权威布局依据或足够可证伪的对照+回归；如果仍有冲突就保持阻塞，不能单凭key相关性写成FULL。

问题二：公开 macOS KPI 下能否用多个硬件RX/TX队列及安全的并发/流映射？

- 候选：保留IOKit，在驱动内部多环/多向量调度；若证据证明接口或ABI阻断，再独立评估DriverKit与其他可维护路径。
- 分别评估 RX硬件hash、CPU分发、TX调度；单个系统output queue不等于硬件只能有一环。AVB实时队列不是RSS。
- 关闭条件：最小两RX队列/两可控流证明分流/有序/锁正确；或给出确切平台阻断证据与下一路线成本。架构迁移必须有对照，不因猜测重写。

## D04 自动启用与原生驱动边界 — OPEN；阻塞：T06

问题：如何在保留 `start()` 不发固件命令/不启DMA的保证下，实现开机即用、断链恢复、服务重启与升级？

- 首先评估受控launchd服务：等设备与版本门满足 → 独占会话初始化 → 发布接口；失败记录并停止，禁止无限reset循环。
- 其他异步初始化路线仅在构建保证/故障恢复可证明时进入比较，不默认取消现有守卫。
- 关闭条件：状态机、唯一owner、超时/取消、启动禁用、安全模式、版本错配、用户退出/关机、服务被杀均有设计与验收；选择具体路径后再写安装配置。

## D05 SDK权限、ABI与RDMA内存安全 — OPEN；阻塞：T13/T14

问题：哪些对象留内核，哪些用户态直达？如何提供verbs/CM语义又保证进程隔离和退出可撤销？

- 优先先做受控最小RC链：context→PD/MR→CQ/QP→真实SEND/RECV→完整销毁；其后逐项READ/WRITE/atomic/扩展。
- 比较自有版本化SDK与可移植verbs/rdma-core用户库适配；不承诺Linux ioctl/内核ABI能原样搬到macOS。
- 决策必须包含：handle代次、配额、pin/map/撤销、rkey/lkey权限、CQ/事件、doorbell/UAR映射、client death、进程身份与特权边界、Ethernet共享资源。
- 关闭条件：有可审查威胁模型/ABI规格和失败矩阵；无任意物理DMA/裸BAR入口；安全最小切片可重复互通后才扩展。

## D06 测试资源和量化指标 — OPEN；阻塞：相应实验，不阻止离线任务

问题：有哪些Linux对端、40/56G或IB链路、PFC/DCB交换机、PTP参考、SR-IOV宿主和可恢复路径？

- 输出“现有/缺少/替代/仍不能证明什么”的清单；不默认购买或更换硬件。
- 核对 PCIe x4 是否当前事实、是否可安排x8对照；不擅自移动显卡/网卡。
- 核定总计划48/72h、循环次数、Linux90%吞吐目标，给出小包/CPU/延迟/PTP的参考与阈值；变更须显式记录。
- 关闭条件：近期实验资源可用、接口绑定和独立管理路径验证；远期不足保持 `BLOCKED-LAB`。

## D07 VPI / IB系统入口 — OPEN；阻塞：T15；依赖 D01、D05

问题：本卡各端口能否选IB/ETH/混合，变更是否持久，IB管理与IPoIB如何让macOS应用使用？

- 先cap/PSID/模式查询；切换/固件配置另申请实验窗口；SM优先用已知好Linux端，之后再决定macOS管理工具范围。
- IPoIB比较原生网络接口与配套服务的IP承载，必须真实经过IB链路且交付应用可用性；记录connected/datagram语义边界。
- 关闭条件：确定实际支持模式、切换/回滚、SM/MAD/PKey/GID及应用路径、验收对端和组合；平台缺口不能直接改成“不适用”。

## D08 VF、peer memory与板级功能的平台边界 — OPEN；阻塞：T16

问题：macOS宿主的VF/IOMMU/hypervisor、GPU peer-memory接口、WoL/sideband/ROM各能承载哪些真实能力？

- VF创建、VF驱动、guest直通/隔离分开决策；不把“枚举成功”称虚拟机可用。
- GPUDirect需要受支持的GPU内存注册/撤销接口；本机GPU路径并不自动拥有CUDA/peer-memory能力。host staging只能作对照。
- CORE-Direct、sideband、ROM功能先证明本卡cap/板级布线/ROM存在，不把商标或家族功能当可用性。
- 关闭条件：每个适用子项有可落地方案与端到端试验，或精确的平台阻断证据；后者保持阻塞而不是关闭总目标。

## D09 发布支持矩阵与维护边界 — OPEN；阻塞：T17/正式发布

问题：支持哪些macOS build/架构/固件，分发开发包还是可常规安装的签名产品，SDK稳定性与升级保证到哪一层？

- 遵守 `PUBLISH-SCOPE.md` / LICENSE / NOTICE，扩展SDK依赖逐一审计；Linux GPL实现仅作参考，不直接混入BSD分发路线。
- 关闭条件：明确真实可安装政策、干净安装/回滚、升级/ABI兼容、许可清单与支持矩阵；无外部签名授权时如实给出限制，不宣称默认全Mac即插即用。
