# Every defect this project has found, and what stops it coming back

This project's real output is not the driver; it is the driver plus the list of ways it
was wrong and the mechanisms that now refuse those ways.  66 defects are recorded below (one row per defect, or one row for a group of
instances that share a root cause),
grouped by family, because the families are what repeat: three times a 64-bit quantity went
through a 32-bit type, three times a failure was represented as something other than a
failure, and twice the *checker* was the thing that was wrong.

## The rule

**A defect either gains a guard, or its row says why no guard is possible -- specifically.**

"Hard to test" is not a reason.  The acceptable reasons are structural and they are rare;
where one applies it is named in the row, and the family section explains what to do
instead.

| # | What happened | Guard |
| --- | --- | --- |

| # | What happened | Guard |
| --- | --- | --- |

| C6 | The A/B experiment freed the ring's MTT entries while the firmware might still be translating through them | Both are kept together, and the log says which |
| C7 | `Cx3Mlx4::init()` initialized 6 members of ~50; the rest -- `fEqRing`, `fNumTables`, `fMrState`, the queue pointers -- were whatever the allocator gave back, and several are tested before assignment | Every member is now listed explicitly.  **No automated guard**: C++ has no "did you initialize it" check for a class with an implicit constructor.  `Mlx4Hw`'s constructor had the same defect (§28.2) and the same fix |
| C8 | `start()` did device work; the machine hung before any log could flush, and six boots hung with nothing to read | The build walks the call graph from `start()` and fails if a write-capable routine is reachable.  Plus `cx3off=1` as a boot-time escape |
| C10 | The same defect as C7, one layer up and found while fixing it: `Cx3Mlx4::init()` initialized 6 members of ~50 -- `fEqRing`, `fNumTables`, `fMrState`, the R4 queue pointers -- and several are tested before assignment | Every member listed explicitly, with the reason written at the list.  **No automated guard**, same structural reason as C7: C++ cannot tell a class with an implicit constructor that a member was forgotten |
| C9 | The shared command mailbox had no transaction-level lock, so two concurrent selectors could interleave around the command lock and each read a mixture | `transactionEnter/Exit` around `IOUserClient::externalMethod`, so one selector call is one transaction.  **No automated guard** -- the symptom is an occasional wrong answer, which no diagnostic distinguishes from a correct one |
| C11 | `exportM3PortUp()` refused while *either* an EQ existed or an interrupt session was open, on the stated rationale that a reset must stay available.  Only one of those two conditions has anything to do with a reset (a reset is refused while an interrupt session is open, and it tears the ring down itself through `teardownEq()`), so the guard turned a false coupling into the one call order the hardware cannot survive: port before EQ.  Measured on 0.43.0, same build, changing only whether the port was up when the EQ was created -- port-up first leaves `QUERY_EQ` flags `0x00000a00` (FIRED) with `invocations=0` and the completion never arriving; EQ first with no port-up reads `0x00000900` (ARMED) and the completion arrives.  The reference is ordered the other way, and provably so: `mlx4_init_eq_table()` creates, maps and arms the async EQ inside `mlx4_load_one()` (`mlx4_main.c:2669`, `mlx4_eq.c:1250/1270/1277`) and the port is activated afterwards by `SET_PORT` + `INIT_PORT` (`mlx4_main.c:2756`, `mlx4_en_netdev.c:1394-1403`).  So the driver could not express the reference's order at all, and could not be made to by fixing anything inside the EQ path -- which is why the previous fix (the re-arm at session open) was necessary and insufficient | The guard is **gone** (it is a log line now) and `tools/verify.sh` walks the reference's order, so the failing order is no longer the one the only entry point runs.  **No runtime guard is possible in the driver, and the reason is specific**: both orders are individually successful on the device -- every command returns firmware status 0, the context is intact, the MTT entries match, the register window is alive -- and FIRED is a legal queue state, not damage.  The failure is the *absence of a relation between two calls the caller makes*, and an absence is exactly what a check cannot read (same structural family as B3/C7).  What caught it instead was the verifier's own interrupt stage failing loudly on a real card.  Writing the order down in one place is the mitigation: the sequence lives in `tools/verify.sh` only, with its reason, and `exportM3PortUp()`'s log line now names the state and the way back rather than refusing |
| C12 | Stage 6 left the send queue's WQE array all zero, which is the opposite ownership state from the reference's: mlx4_en_netdev.c:1373-1375 stamps **every** 64-byte TXBB's first dword with `INIT_OWNER_BIT = 0xffffffff` ("SW owns") right after the memset (mlx4_en_tx.c:227), and this port stopped at the memset.  Zero means bit 31 = 0 = **HW owns**, so at stage 9 every slot would look in-flight to the driver's own reclaim scan.  The dummy header's stamp value was also taken from the RX ring's marker (`1 << 31`) rather than the transmit convention (`STAMP_VAL | owner<<31`, en.h:99), which happens to agree on the ownership bit and differs in the low 31.  **Found by reading DPDK's independent mlx4 implementation alongside FreeBSD's** (docs/EXTERNAL-REFS.md section 5) | Stamp every TXBB `0xffffffff` at creation, use the transmit stamp encoding for the header, and state in the check that what it reads back is the driver's own write and says nothing about the hardware's interpretation -- which is why stage 6's stamp check passed while this was wrong.  **Shipped in 0.43.6** (docs/R4-STAGE7-RESULT.md section 5): `Mlx4Hw::sqCreate` stamps every 64-byte unit of the send queue's memory, the header included, `Cx3R4TxResult` gained `sqTxbbsStamped`, `sqWqeNonZeroBytes` now counts bytes *outside* those stamps, and the single scalar `kR4TxOutSqStampMatches` is the conjunction of the header's value and that count -- so the half stage 9 actually trips over (the WQE array) can no longer pass behind the header's half |

## The structural gaps, and what to do instead

Everything above has a guard except **B3, C1, C7, C9, C10, C11** and the family-F rows whose
own text says why none is possible (F3, F7, F8, F10, and this batch's F11 and F12; **F13
arrived with one**, three of them, because a limit that can be asserted is not a limit that
has to be written into prose).  They are
not oversights; they are five kinds of problem that a runtime check cannot reach.  The newest
is the fifth, which arrived with this batch:

1. **A side effect far from its cause** (C1).  A read that changes nothing at the read but
   breaks a command much later.  What would catch it is a register-access audit -- every
   MMIO address touched, in order, dumped on failure.  Not built: the user deferred it.

2. **A missing invalidation** (B3) and **a missing initialization** (C7).  Both are
   *absences*, and no runtime check can see an absence.  What helps is putting every
   invalidation in one function, which is done, and listing members longhand so an omission
   is visible, which is done.

3. **A race whose symptom is a plausible value** (C9).  Here the guard is the fix rather
   than a test: the transaction lock removes the interleaving instead of detecting it.  A
   test that reproduced it reliably would be a better answer, and none exists.

4. **An ordering relation between calls the caller makes** (C11).  The driver is asked to
   create an EQ and to activate a port, in some order, and one of the two orders leaves the
   interrupt permanently unable to arrive -- while every command of both orders returns
   firmware status 0 and the device reports a legal state (`FIRED`) rather than damage.  No
   check inside the driver can see the ordering, because nothing is wrong at the moment
   either call runs.  What works instead is that the order lives in exactly one place and is
   copied from the reference's own call order rather than reasoned out, plus a verifier stage
   whose job is to make the failure loud -- which is how this one was found, on the card, as
   `interrupt delivery FAIL invocations=0` rather than as a silent absence.

5. **A sentence that reads as a different claim than the number beside it** (F3, F7, F8,
   F10, F11, F12).  This is the family's oldest running complaint and the one the rule above
   has not fixed: at six rows, the mechanism still has not changed.  The difference between
   a value and a count, between a fact and a verdict, and between a complete line and an
   accurate-but-incomplete one are all things a compiler cannot see and a regex cannot
   decide -- the two candidates tried so far (removing verdict text; deriving every reported
   number from the payload it describes) each caught the instances in front of them and
   neither reached the general case.  What this batch could do was the part that generalises
   a little: two of the three fixes here removed a *second copy* of a number rather than
   rewording it (F11 moved the step count into the ABI; C12's check now measures the whole
   array instead of one representative unit), which is the same instinct as D12's -- make the
   disagreement unrepresentable rather than detectable.

## What this file is for

When a defect is found, it gets a row: which family, what the guard is, or why there can be
none.  When a family reaches three rows, that is the signal to stop guarding individual
instances and change the mechanism -- which is exactly how the compiler warnings and the
readback-first rule arrived.

## 0.43.9's two rows, and the limit they name

Both rows of that batch arrived **with** a guard, so neither joins the unguarded list above:
**D14**'s is a rule in `tools/check-hardcoded.py` (calling a non-barrier fails the build) and
**E14**'s is a compiler-derived offset in `tools/test-cqe-offsets.c`.

What E14 adds to this file is a limit of a different kind, and it is worth writing down because
it will recur for as long as the transmit path is being chased: the guard covers the *offset*
and reproduces the reference's *condition*, but nothing in this driver can establish what the
**firmware** does with the byte.  The chip's own programming manual is NDA and the public one is
for a later part, so no test in this tree can decide whether the firmware keeps `pri_path.feup`
-- only the card can, through `QUERY_QP`, which is why the value is reported as three scalars
rather than asserted as a pass/fail.  That is not a check waiting to be written; it is a fact
that a run answers, and the verifier's SKIP text says which run should be the last one spent on
it if the answer is "the firmware dropped it".

The batch also produced a rule about *method*, which belongs here because it is the reason two
of its three findings were found at all: **agreement between two implementations is not a
result.** The "the PRM's step 2 was never done" theory (that the send doorbell record must be
written) stood on two sources agreeing that the receive record IS written; it died when a third
implementation -- DPDK -- showed that the send record is written by none of them. The `feup`
finding came from the opposite direction: not from more implementations of the same path, but
from asking whether the reference's ONE shared fill produces the same context for both kinds of
queue, which it does not. So: when a field looks unused, first ask whether the two queue kinds
instantiate the shared code differently -- that question is what E13 and E14 have in common.

## 0.43.10's one row, and the shape it adds

**F13** (the scalar cap treated as a setting) arrived with three guards, so this batch adds
nothing to the unguarded list.  What it adds to the file is the family's own failure mode
reached through *configuration*: the guard was a `CX3_STATIC_ASSERT` whose two sides were both
our own numbers, so raising one raised the other and the check could not fail.  F4 recorded
that shape for a check that was never called; this is the same shape where every part was
present, compiled and green.

The defense is the one this project uses everywhere else, applied to a limit: **the value has
one home, and that home is not ours.**  The cap is now asserted equal to the kernel's constant
in the only translation unit that can see both, and the per-selector widths are asserted
beside their enums, so "we need one more scalar" surfaces as a build failure at the selector
that needs it rather than as a selector that cannot be called.  A limit that arrives from
outside the program is not documentation; it is an assertion, and the second home for it is a
bug.

The second thing this row records is a *coverage* one, and it is the reason it was not filed
as bookkeeping: a batch whose work cannot be reached measures nothing, and 0.43.9's own
documents describe the `feup` criteria as if they had been exercised.  When a selector turns
out to have been unreachable, the honest edit is not only the fix -- it is to say, in the same
breath, which of the batch's claims were never asked (`docs/COVERAGE.md`'s `r4tx` row, and
section 14 of `docs/R4-STAGE9-RESULT.md`).

## 0.44.x's three rows: diagnostics that said something untrue

Three defects from the M4/M5 batch, and they share a family -- D, "something that looked like a
measurement" -- reached from three different places.  What they add to the file is that two of
them are in the *harness*, not the driver, and all three were found by **running** something
rather than by reading it.

**F14 -- a tool that printed a report from outputs the kernel never wrote.**  `cx3ctl netfilt`
and `cx3ctl netarm` checked the call's return code and then printed their report anyway.  On a
kext older than the tool the selector does not exist, so the outputs are whatever the tool's own
memset left -- zeros -- and the netfilt report read as "the switch is off and nothing has been
programmed": a statement about the driver, when the truth was that nothing had been asked.  The
netarm case was worse in kind rather than degree: zero IS its "the experiment ran" code, so it
would have printed a complete experiment report -- drained 0, queue empty, armed, no event --
for a run that never happened.

*Guard*: any command that interprets outputs first asks whether the call ran, and says which of
the two situations it is in.  `netstat`, `netlink` and `netoff` already did; the two new ones do
now.  *Found by*: running each new command against the kext that was loaded at the time, which is
the one test that needs no reboot.

**F15 -- a variable set in a subshell, and forty-three messages that reported the value from
before the call.**  `runcall` is always invoked as `j=$(runcall ...)`, a command substitution, so
every assignment it makes to `LAST_CALL_RC` / `LAST_CALL_SIZES` happens in a subshell and never
reaches the caller.  Every "the call failed: rc=$LAST_CALL_RC" message in the chain therefore
printed the *previous* value -- normally `rc=0`, which reads like the kernel answered 0, i.e.
like success.

*Guard*: the failure details go to a file (the one channel a subshell can still write) and are
read back by `callinfo()`; the messages now carry the real code, and the number is checked by
eye against the JSON the tool itself prints.  *Found by*: running the new `m5` mode once and
reading its own output.  *Not fixed by*: any amount of reading, since the code reads correctly --
the bug is in how the shell works.

**F16 -- a selector table missing a row, so the harness called a selector with nothing asked
for.**  `cx3ctl sizes` had no row for `netup` (selector 39).  `tools/verify.sh` learns each
selector's in/out counts and structure size *from that table*, so the chain's interface step
called it with no outputs requested and could only report "the call failed" -- a failure whose
message said nothing about the device, at the step whose whole purpose was to say whether an
interface exists.

*Guard*: the build now runs the freshly built `cx3ctl sizes` and requires a row for every id from
0 to `kCx3SelCount-1`, with none past the end.  The kext's own `CX3_STATIC_ASSERT` pins the
*dispatch* table and could not catch this: it is a different list in a different file, which is
what made the gap invisible.  *Found by*: adding a chain step and asking what it would do on the
machine -- the same question that produced F13's coverage row.

The common lesson is the file's oldest one, stated three ways: **a diagnostic that cannot say
"nothing was asked" will say "nothing happened" instead.**  A zero from an un-run call, a stale
variable, a missing row -- each is indistinguishable from a real reading unless the code
deliberately distinguishes them, and in all three cases the distinguishing fact was available
and simply not consulted.

## 0.44.21's two rows: the session boundary

Both were found the same way -- by asking what the *other* side of a boundary would see, instead of
reading the side being changed -- and both sit in the same place: what `m3irqdown` leaves behind.

**F17 -- a guard that counted an object the release deliberately keeps, so a second session in one
boot was impossible.**  `exportM3IrqUp` refuses when `fIrqObjectsUp || fIrqSource || fWorkLoop`,
but `irqReleaseObjects()` drops the first two and keeps the workloop on purpose (it is the loop
`getWorkLoop()` hands the networking family, released only in `stop()`).  After one session, the
workloop alone tripped the guard, and every later `m3irqup` in that boot was refused with
"interrupt objects still exist (enabled=0)".

*Measured* (2026-10-13, one boot): `m3irqup OK` at 12:05:27, then refusals at 12:08:15, 12:08:55,
12:16:00, 12:17:02.  The refusals *before* 12:05 named different reasons (`no EQ is up`; `the
interrupt clear is not set up`), which is what identifies the workloop as the thing that changed.
*Cost*: one reboot per session attempt, on a machine where a reboot is the expensive resource.
*Found by*: asking what an experiment would cost, not what it would measure.

**F18 -- a session that closed by removing the listener while the device kept the queue.**  The
source is legacy INTx (`getInterruptType` reports `0x1`, not `PCIMessaged`): the line stays
asserted until the event is consumed *and* the clear register is written.  `m3irqdown` removed the
event source and left the EQ with the firmware -- it said so in its own log ("the EQ itself is
untouched") -- so from the close until the end of the boot the card owned an armed queue and could
assert a line that nothing would acknowledge.  The reference sends `HW2SW_EQ` as the *first*
statement of its teardown (`mlx4_eq.c:1080`), before any memory is freed, for this reason.

*Guard*: the close is now ordered acknowledge -> drain -> stop delivery -> **hand the queue back**
(`Mlx4Hw::eqHw2Sw`, which is the reference's first teardown statement), and it reports how many
EQEs were still in the queue at the moment of closing -- the reading that says whether the line was
up when the session ended.

*Measured 2026-10-13 13:20 on 0.44.24*: the chain ran through `interrupt session closed` and the
machine did **not** freeze -- four runs after that same step had killed it three times. That
closes the question this row was opened for, and it also cost one iteration to get the *scope* of
the hand-back right: the first version called the whole `teardownEq(..., false)`, which hands the
queue back **and frees the host ring and the EQ number**, and the chain then stopped with `r4cq
refused: no EQ is up, so comp_eqn would name a queue that does not exist` -- a completion queue's
context carries an EQ number, and the R4 stages that build it run *after* this call. The close now
hands back the queue and keeps the host state; the ring is released by the next reset or by
`stop()`, both of which already did. The general shape, named so the next boundary change is
checked for it: **a teardown that is correct for the device can still be wrong for the sequence it
sits in.**

*Not proven*: that the same mechanism explains the other freezes (the 10:47 one had no session
open at all). What is now measured is that the three freezes at/after the session close are gone.
*Residual, unfixed and written down*: the storm-guard path inside `irqAction` still disables the
source without a hand-back, so a genuine storm would leave the same shape.  It has never tripped on
this machine (`storm tripped no` on every close so far).

## 0.44.22's three rows: a report, a slot and a gate that did not cover what they claimed

All three were found by reading the code that has never run on this machine (`netup` and the M4
gate), not by running anything -- which is the only kind of review available while the freeze fix
waits for a reboot, and the cheapest place to find a defect, because the alternative is finding it
with a reboot and a guess.

**F19 -- `netup`'s success line said the data path was not connected, and it was.**  The log line
ended "THE DATA PATH IS NOT CONNECTED: outputPacket drops and counts, and no received frame reaches
the stack -- that is stage 10b, which is where mbufs first appear."  That was true when it was
written and false the moment 10b landed: `outputPacket` now posts into the send queue, the timer
polls the receive CQ and hands frames to the stack.  The line a reader sees at the instant the
interface appears is the one place a stale sentence does the most damage -- it says "a ping cannot
work" about the build whose whole purpose is to make a ping work.

*Fixed by*: stating what the code does, and what has never happened -- "wired in this build ... and
it has NEVER RUN on this machine" -- so the reader is sent to the counters (`cx3ctl netstat`, the
`net rx:`/`net tx:` lines) instead of to prose.

**F20 -- the same function reported the link up whatever the port had measured, one branch below
the fix for exactly that.**  `exportNetUp`'s fresh-attach path computes
`fPortLinkUp ? 1 : 0`; the "already attached in this boot" path wrote a hard `1`.  The 0.44.6
comment records the same defect being fixed in the other copy ("the second copy reported ACTIVE
unconditionally, whatever the port stage had measured") -- so this is that defect surviving in the
one place the fix did not reach.  It survived because the slot is a report and not a gate: nothing
judged it.  *Guard*: the slot now comes from the same `fPortLinkUp`, the link is republished on
that path too, and tools/verify.sh reads the slot (it had the alias and never used it) to separate
"the port measured the link down" from "we published ACTIVE and the family still says inactive",
which are two different findings that used to produce one message.

**F21 -- the M4 gate could pass without this driver carrying a single frame.**  The soak ran
`ping -c N <target>` unbound.  This machine has a second Ethernet controller on the same subnet
(en0), so the routing table -- not the gate -- decided which interface carried the traffic, and a
0% loss result would be reported as "M4 IS MET" whether or not the card in question worked at all.
The driver's own counters were *printed* next to the verdict and never judged, which is the same
defect one level up: a green result that does not cover the requirement.

*Fixed by*: `-b <if>` (an Apple addition: "Bind the socket to interface boundif for sending"), so
a 0% loss result means the frames left THIS interface and came back to THIS interface's address;
and the gate now requires the driver's own counters to agree with the ping (posted >= transmitted,
delivered >= received).  A ping that succeeded while the counters did not move is reported as
`contradiction`, not as a weaker PASS.

*Found by inspecting the fix*: the pattern that reads ping's transmitted count was written like the
one that reads its loss figure (`.*[^0-9]\([0-9]*\) packets transmitted`) and returns EMPTY on the
real line, because that line *starts* with the number and `[^0-9]` has nothing to consume before
it.  Measured against this machine's own ping output; the loss and received patterns matched and
this one did not.  The empty value matters because the comparison fell back to `${soak_sent:-1}` --
i.e. the gate would have quietly weakened itself to ">= 1 frame" instead of ">= N" and still
printed PASS.  Now read from the start of the line, and an unparseable count is its own verdict
rather than a fallback.  The decision block was then extracted by line range and run against five
controlled readings (counters agree / counters do not move / total loss / loss without counts /
counters unreadable): the second is the false PASS this row is about, and it now reports FAIL.
