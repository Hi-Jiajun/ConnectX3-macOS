# Normal EQ return evidence and release boundary

2026-10-24. Scope: normal `HW2SW_EQ` teardown for ConnectX-3/3 Pro only. This is a bounded source review, not authorization for hardware testing. **Conclusion:** a successful `HW2SW_EQ` is the available queue-level firmware return signal and is required before this port normally frees an EQ ring/MTT range. The reviewed sources do not establish that it flushes all PCIe DMA already issued by the device. Keep that as an explicit specification gap; do not promote command success, driver convention, generation tags, or software callback drainage into a generic DMA release credential.

| A successful result means the command completed and firmware status was zero; timeout or nonzero firmware status is failure. | Port `cmdBoxLocked`: posts GO then polls (`Mlx4Hw.cpp:982-1005`), timeout returns false and records `TIMEOUT` (`:1068-1087`), then reads reply/status and only returns true for status zero (`:1095-1113`). Linux v6.12 polling analog waits for GO clear and decodes HCR status (`cmd.c:610-663`, source: [torvalds/linux v6.12](https://github.com/torvalds/linux/blob/v6.12/drivers/net/ethernet/mellanox/mlx4/cmd.c#L610-L663)). | Command-completion evidence | A timeout is ambiguous: the request may have been seen and may still complete. The port correctly retains the ring on failure (`Cx3Mlx4.cpp:8439-8459`). Successful command completion still does not, by itself, prove posted PCIe writes have drained. |
| Upstream Linux treats HW2SW_EQ as preceding host-side MTT/ring reclamation, and separately drains CPU interrupt/tasklet users. | Linux v6.12 `mlx4_free_eq()` issues HW2SW_EQ, calls `synchronize_irq()`, disables the tasklet, then cleans MTT and frees coherent ring pages (`eq.c:1088-1114`; [source](https://github.com/torvalds/linux/blob/v6.12/drivers/net/ethernet/mellanox/mlx4/eq.c#L1088-L1114)). It is not a CX3 PRM guarantee that DMA is globally drained. |
| FreeBSD's failure branch is not safety evidence for this stricter port. | Vendored FreeBSD `mlx4_free_eq()` warns if HW2SW_EQ fails (`mlx4_eq.c:1080-1082`) but proceeds to `synchronize_irq`, MTT cleanup, page free, and EQ-number release (`:1084-1093`). | Counterexample / source convention | Do not cite the reference driver's unconditional failure cleanup as proof of safe reclamation. The current port deliberately fails closed and retains on HW2SW failure (`Cx3Mlx4.cpp:8440-8457`). |
| The current macOS IRQ-source path has a separate software drain before ordinary stop teardown. | `irqReleaseObjects()` disables the source and only releases it after successful workloop removal; any failure keeps dependent queue owners (`Cx3Mlx4.cpp:6397-6417`). `stop()` waits for admitted network callbacks, confirms IRQ removal, stops timer service, then calls `teardownEq()` (`:7339-7384`). The source audit records the local SDK single-threaded workloop and synchronous removal contracts (`docs/reports/r06-generation-scope-audit.md:37-39`). | Documented API contract + source-level inference | Required CPU/IRQ exclusions: no remaining EQ consumer or selector path may access the ring; interrupt source must be disabled and successfully removed/drained; timer and network/interface callbacks must be closed and drained; teardown ordering/locks must exclude concurrent users. These conditions cover host-side users only, not DMA. |
| An ordinary non-reset free additionally depends on exact MTT ownership/release; reset is not the normal return credential. | `teardownEq()` issues HW2SW_EQ before `mttFree()`/ring free (`Cx3Mlx4.cpp:8439-8476`), and the current owner ledger preserves rejected ranges (`docs/reports/r06-mtt-owner-inventory.md:34-38`). Reset path retains the MTT range (`Cx3Mlx4.cpp:8482-8490`). | Current implementation contract | Even after queue return, allocator refusal or outstanding dependencies must retain the ring/MTT owner. Reset recovery is a different scope and cannot be substituted here. |
| No reviewed CX3-specific primary source states that successful HW2SW_EQ drains all in-flight PCIe DMA writes or is a fabric-level fence. | The local FreeBSD source, Linux v6.12 driver, command encoding, and completion logic describe a synchronous command return and subsequent software cleanup, but no CX3 PRM text defining “all prior DMA completed / no writes remain outstanding” was available in the bounded pass. Existing DMA design notes explicitly separate queue ownership from posted-write drainage (`docs/reports/dma-quiescence-design.md:7-23`). | **Unproven** | Exact unknown: after a successful HW2SW_EQ completion, can the HCA still have an already-issued DMA write to that EQ's ring/MTT pages that may complete later? What ordering/fence (if any) guarantees no such write can land after host reuse? Until a CX3-specific spec answers this, HW2SW_EQ success is queue-return evidence, not a proven all-DMA drain. |

## Bounded source pass and practical next step

Reviewed the vendored FreeBSD `mlx4_eq.c` and command definitions, the Linux v6.12 `mlx4/eq.c` reference, and this port's command/teardown paths. One targeted search for an official Mellanox CX3 programming reference was attempted, but the configured keyless search service returned `monthly_cap_reached`; no CX3 PRM was retrieved or relied on. This is a source availability limit, not evidence that the specification does not exist.

Follow-up: a separate GPT Luna/high [bounded primary-source search](r06-cx3-prm-search-20261024.md) used the normal search pool for four targeted NVIDIA-domain queries. It retrieved the official support/design-in access route for a ConnectX EN PRM, but no CX3/CX3-Pro-specific HW2SW_EQ DMA ordering text. Existing public CX4 PRM material cannot close this product-specific gap. The unresolved predicate remains unchanged; other offline implementation continues.

Smallest safe offline step: keep `HW2SW_EQ success` and the CPU/IRQ drain as separate predicates in the release-site behavior fixture; inject command failure, IRQ-removal failure, and outstanding CPU admission and assert zero MTT/ring frees for each. Keep a distinct unresolved DMA predicate that cannot become true from `HW2SW_EQ`, generation, bus-master readback, or a quiet sampling window. The fixture can prove the software gate composition only. It cannot establish the CX3 firmware/PCIe DMA contract; that requires the exact CX3 PRM statement (or a separately approved, instrumented hardware assertion, which this task does not authorize).
