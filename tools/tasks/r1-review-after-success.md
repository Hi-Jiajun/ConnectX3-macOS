## 已经达成的目标（真机实测）

M3 的第一个里程碑是：**在不用中断的前提下，证明事件队列整条 DMA 链路是活的**。
做法是发一个**事件模式**的命令（置 HCR 的 E 位并带自选 token），再轮询 EQ 环，
寻找带匹配 token 的 CMD EQE（这是参考 `mlx4_test_async()` = `mlx4_NOP()` 的同一手法）。

**已观测到（从内核日志逐字摘录）：**

1. `QUERY_FUNC`：`max_eq 156, reserved_eqs 28, reserved_uars 7`（与 `QUERY_DEV_CAP` 的
   512/8 不同，故必须问）。EQN 取 `reserved_eqs` = 28。
2. `SW2HW_EQ` fw status 0；`MAP_EQ`（CMD + PORT_CHANGE）fw status 0。
3. 事件模式 NOP：投递时回读命令 dword = `0x00600031` ⇒ **GO=0（完成）、E=1（bit22）**，
   opcode 0x31，token 字段 0x0060。即 E 位确实上了硬件。
4. **环里出现了完整正确的 CMD EQE**。slot 0 的 64 字节槽，legacy EQE 在**后半区**
   （偏移 0x20 起）：
   ```
   000a0000 0031 1234 0000001f 000000 00 f606b47e 00000000 00000000
     ^^        ^    ^^^^          ^
     type=0x0a  ?  token=0x1234  status=0x00
   ```
   （token 与本次发送的 `0x1234` 一致，status=0 表示命令被接受。）

## 过程中的三个坑（都已定位并修，写出来供你判断修得对不对）

### 坑 1：固件在 `SW2HW_EQ` 时**异步**初始化整个 EQ 环

四点插桩（都在 `Mlx4Hw::eqCreate()` 内，同一块内存）：

| 读数点 | 前 32 字节 |
| --- | --- |
| 主机 `memset(0)` 之后 | `0000…0000` |
| 写 0x5a 再读回（自检） | `5a5a…5a5a`（写读一致） |
| `SW2HW_EQ` **之前** | `0000…0000` |
| `SW2HW_EQ` **成功之后** | `cccc…cccc` |

⇒ 主机清零有效、中间无人改写，**是固件在接收队列时把环初始化了**（0xcc/0xee 填充，
并按槽写入递增数据）。而且它是**异步且分阶段**的：同一次调用内、同一 16 字节的两次读取
曾给出不同结果；"owner 位置起"这个条件曾在 1 ms 就通过，而实际稳定要到约 238 ms。

**这带来一个真实后果**：按参考的判据 `ready <=> !!(owner & 0x80) == !!(cons_index & nent)`
（`mlx4_eq.c:121-125`），**全零环在第一圈（`cons_index < nent`，相位位为 0）的每个槽都判为
"可消费"**。于是固件初始化期间的一次轮询会把**从未写过的槽**当成事件消费掉，consumer
index 越过它们——而真正的 CMD EQE 恰恰落在被越过的那一格后面。

### 坑 2：我们的轮询条件写错了两次

最终采用的等待条件是：**"武装图案出现" 且 "连续两次读取一致"**，并记录一路上见过几种
不同读数（>1 表示固件分阶段写入，即存在"不能轮询的窗口"）。

### 坑 3：`m3eqpoll` 的 found 分支漏填输出（纯软件 bug，已修）

内核日志说"找到了 EQE"，而用户态工具报"none、type 0x00"——因为 found 分支没给
输出字段赋值（连它自己那行日志打印的 type 也是同一个洞）。这与硬件无关。

另外两处已修：`m3eqpoll` 之前**读了调用者给的起始索引却没用**（导致 `from 0` 无效）；
以及**拒绝消费 type 为 0x00 的"可读但为空"槽**（这正是越过现象的成因；参考从不会遇到，
因为它只在已武装的环上轮询）。
