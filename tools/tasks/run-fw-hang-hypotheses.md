## 已经实测到的事实（全部是真机输出，不是推断）

命令接口是 HCR（BAR0 偏移 `0x80680` 起 7 个 dword；移植侧常量见 `src/mlx4_regs.h`）。
顺序按参考：`mlx4_reset` → HCR 握手 → `QUERY_FW` → 分配 FW 区 → `MAP_FA` → `RUN_FW`
→ `MOD_STAT_CFG`（`mlx4_core/mlx4_main.c` 的 `mlx4_init_fw` / `mlx4_load_fw`）。

1. **`QUERY_FW`(0x4) 成功**，返回：`fw_ver=2.42.5000`、`cmd_if_rev=3`、`max_cmds=16`
   （`log2=4`）、`ppf_id=0`、catas `off=0x1f020 size=0x10 bar=0`、
   `fw_pages=1542`（从 outbox 偏移 `0x00` 读 u16 BE，与 mainline Linux
   `fw.c:1638/:1709` 和 FreeBSD `mlx4_fw.c:1620/:1691` 一致）。原始前 4 个 dword：
   `06060002 1388002a 00000003 00000004`。
2. **`MAP_FA`(0xfff) 成功**：1542 个页条目、7 批（每批 ≤256 条），每批返回 fw status 0。
   邮箱条目编码是「每 4 KiB 页一条、对齐字段 0」。前几轮独立审查已判定该简化安全。
3. **`RUN_FW`(0xff6) 永不完成**：CLASS_A 超时 60000 ms 到点，期间 HCR 的 GO 位一直是 1。
   超时瞬间读回的命令寄存器是 `0x00a00ff6`（GO=1、T=1、E=0、opcode=0xff6）；
   稍后 dump `0x80680` 起 14 个 dword 得到：
   ```
   +0x80680  00000000 00000000 00000000 00000000
   +0x80690  00000000 0000ffff f60f8000 01000000
   +0x806a0  00000000 00000000 00000000 00000000
   ```
   （`0x80694` 是 token、`0x80698` 是命令/状态 dword、`0x8069c` 是 ownership word。
   注意 `0x8069c` 与 `0xf03fc` 这两个地址在这台机器上「首次读返回 0、后续读返回
   `0x01000000`」，两个操作系统、两条访问路径都如此，已判定为设备属性。）
4. **超时之后，`0x80698` 仍停在 GO=1 且 opcode 仍是 0xff6**，即卡从未处理完这条命令。
5. **catas 缓冲区（`0x1f020`，由 QUERY_FW 报告）读出全 0** ⇒ 没有灾难性错误记录。
6. **已证伪的假设：DMA 地址过高。** 用「把 FW 区限制在 4 GiB 以下」跑同一序列：
   1542 页全部落在 `0x2c7c8000..0x2cdcd000`（且完全连续、单段），`RUN_FW` **照样超时**。
   另一组不限制时地址是 `0x4a23fc000..0x4d893b000`（1542 页全部 ≥4 GiB），也超时。
   ⇒ 「4 GiB 以上的总线地址不可达」不是原因。
7. **已修正的缺陷**：此前 `QUERY_FW` 从偏移 `0x10` 读 `fw_pages`（得 5123），
   导致 FW 区被放大 3.3 倍；改成 `0x00`（1542）后 `RUN_FW` 仍然超时。
   ⇒ 页数不是根因，但已修正。
8. **已修正的缺陷**：`cmdBox()` 超时提前返回时不写 `outFwStatus`，调用方局部变量初值 0，
   于是超时曾被打印成「fw status 0x0 ok」。现在超时/未发出/无设备分别有哨兵值。
